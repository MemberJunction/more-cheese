Target MemberJunction 6.1.2

`mjVersionRange` moves from `>=6.1.0-edge.4 <7.0.0` to `>=6.1.2 <7.0.0`, and every
`@memberjunction/*` peer dependency across the three packages moves from
`^6.1.0-edge.4` to `^6.1.2`.

**Why 6.1.2 and not `edge`.** The `edge` dist-tag is `6.1.0-edge.7`, which is *older* than
6.1.2, and `bizapps-forms` already requires `>=6.1.1`. MJ coerces a prerelease host to its
base tuple (`6.1.0`) before testing a range, so an edge host fails forms outright. 6.1.2 is
the only version the whole nine-app graph accepts. Resolving the real graph against it
yields exactly one copy of `@memberjunction/core@6.1.2` — 211 `@memberjunction/*` packages
at a single version in this repo's lockfile, none left on an edge build.

**This drags Angular with it, and that is not incidental.** `@memberjunction/ng-base-forms@6.1.2`
peer-requires `@angular/animations@^21.2.22` (as do `ng-entity-viewer` and `ng-link-directives`
for `core`/`common`/`forms`). This repo anchored the `@angular/*` devDependencies at exactly
`21.1.3`, so with the MJ peers alone the lockfile could not be resolved at all: `npm install`
died with ERESOLVE, and per the install engine's behaviour a host hitting that during
`mj app install` records the app and leaves it **Disabled** while the output still reads as
success. The anchors therefore move to `21.2.22` — which is what MJExplorer ships, and what
the sibling apps already override to. The `@angular/*` *peer* ranges in `more-cheese-ng` are
untouched: they were already `>=21.0.0 <22.0.0`, a range, not a pin.

Patch rather than minor: no migration is added by this change (see
`docs/template-docs/branching.md` — minor is the floor for a migration, not for a
dependency move).
